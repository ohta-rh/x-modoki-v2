# ADR-0038: 画面のテストは、テストごとに画面から登録し、画面では作れない量のデータだけをデータベースへ直接入れる

- ステータス: 採用
- 日付: 2026-11-18
- 決定者: エージェント（委任された判断。ADR-0028 によりユーザーに聞かずに決めた）
- 関連: ADR-0024、ADR-0031、ADR-0036、[テストの設計](../architecture/test-strategy.md) の 5 節、#18、#19

## 背景

[テストの設計](../architecture/test-strategy.md) は、ログインを「テストの前に 1 回だけ API で登録・ログインし、`storageState` を保存して使う」と書いていた。

- #18 で、Better Auth 自身の登録とログインの HTTP の入口を閉じた（検証と回数の制限を通らないため）。API で登録する道は無い
- #19 の受け入れ条件は「60 件のシード」で下へ続きを読むことを確かめる。画面から 60 回投稿すると、投稿の回数の制限（1 分に 10 回）に当たる。シードの 300 件は `おすすめ` に全員分が混ざり、CI では流していない
- Playwright は 3 つのブラウザで並列に動く。同じ人を共有すると、互いの投稿が混ざる

## 決定

- **ログインした状態は、テストごとに画面の登録のフォームで作る**（`e2e/support/auth.ts` の `signUp`）。人は毎回新しく、名前は架空（`e2e_…`、`@example.test`）
- **画面では作れない量のデータだけを、`e2e/support/db.ts` からアプリのデータベース（`pnpm start` が使う `DATABASE_URL`）へ直接入れる。** 今は `insertPosts`（その人の投稿を N 件）だけ。入れた数の列（`posts_count`）も合わせる
- 操作の振る舞いそのもの（投稿・いいね・フォロー）は、画面から行う。直接入れるのは、前提のデータだけ
- 全員の投稿が混ざる画面（`おすすめ`）では、自分の投稿の位置を確かめない。`フォロー中` か自分のプロフィールで確かめる

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| テストごとに画面で登録し、量だけ直接入れる（採用） | テストが互いのデータを見ない。登録の入口を開けずに済む | テストごとに登録の数秒がかかる |
| 1 回だけ登録し、`storageState` を共有する（前の設計） | 速い | 並列のテストが同じ人のデータを書き合う。登録の HTTP の入口が要る |
| 60 件も画面から投稿する | 前提も本物の操作 | 回数の制限に当たる。遅い |
| 回数の制限を画面のテストだけ上げる（ADR-0036 と同じ形） | 直接の書き込みが要らない | 60 回の投稿で 1 分以上かかる |

## 結果

- `e2e/support/db.ts` は、データベースの形（表と列の名前）に頼る。表を変えるときは、ここも直す
- 直接入れたデータは、開発のデータベースに残る（画面のテストの人と投稿）。テストはそれに頼らない
