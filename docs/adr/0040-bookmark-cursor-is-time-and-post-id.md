# ADR-0040: ブックマークの一覧のカーソルは、付けた時刻のマイクロ秒と投稿の ID の組にする

- ステータス: 採用
- 日付: 2026-11-18
- 決定者: エージェント（委任された判断。ADR-0028 によりユーザーに聞かずに決めた）
- 関連: ADR-0010、ADR-0015、[データモデル](../architecture/data-model.md) の 3 節（`bookmarks (user_id, created_at DESC)` の索引）、#21

## 背景

- ほかの一覧（タイムライン・返信）は投稿の ID の順で、カーソルは最後の投稿の ID
- #21 の受け入れ条件は、ブックマークを「付けた順の新しい順」に 20 件ずつ出すこと。付けた順は投稿の ID の順と違うので、投稿の ID はカーソルにならない
- `bookmarks.created_at` は PostgreSQL の `timestamptz` で、精度はマイクロ秒。JavaScript の `Date` はミリ秒なので、`Date` を通すと同じミリ秒の中の順が失われ、続きで欠けたり重なったりする
- 同じ時刻に付いた複数のブックマークもありうる（一度に入れたデータ、時計の粒度）

## 決定

- **カーソルは `<created_at のマイクロ秒の整数>_<投稿の ID>`。** マイクロ秒は SQL で `(extract(epoch from created_at) * 1000000)::bigint` として読み、JavaScript の `Date` を通さない
- 続きは `(created_at, post_id) < (to_timestamp(0) + マイクロ秒 * interval '1 microsecond', 投稿の ID)` で読み、`created_at DESC, post_id DESC` で並べる。同じ時刻でも欠けず重ならない
- 形の違うカーソルは、データアクセス層が `BAD_CURSOR` を返し、Route Handler は 400 にする。空のカーソルは最初のページ

## 検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **時刻のマイクロ秒と投稿の ID の組（採用）** | 付けた順に正しく並び、同じ時刻でも欠けない。`(user_id, created_at DESC)` の索引が使える | カーソルの形がほかの一覧と違う |
| 投稿の ID だけ | ほかの一覧と同じ形 | 付けた順にならない |
| ISO 8601 の時刻の文字列（ミリ秒） | 読みやすい | マイクロ秒が落ち、同じミリ秒の中で欠けたり重なったりする |
| オフセット（何件目から） | 作りが簡単 | 読んでいる間に付け外しがあると、ずれる |

## 結果

- 良くなること: ブックマークの一覧が、付けた順に、欠けず重ならずに続く
- 受け入れる負担: クライアントはカーソルを中身の分からない文字列として扱う（今もそうしている）
- 守ること: 付けた順・いいねした順のように、投稿の ID と違う順の一覧を作るときは、同じ形（時刻のマイクロ秒と ID の組）のカーソルにする
