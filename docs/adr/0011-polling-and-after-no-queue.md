# ADR-0011: 新着と未読は定期的な確認で知らせ、あとの処理は同じトランザクションと `after()` で行い、キューを持たない

- ステータス: 採用（定期的な処理の呼び方を ADR-0017 で置き換え）
- 日付: 2026-11-18
- 決定者: エージェント（委任された判断）
- 関連: [バックエンド技術選定](../research/backend.md)、ADR-0006、ADR-0010、ADR-0015

## 背景

すぐに伝えたいものは、タイムラインの「N 件のポストを表示」と、通知の未読の数。どちらも数十秒の遅れが許される。ダイレクトメッセージは後の段階で作る。

操作のあとに行う処理は、通知の行を作ること、数を増減すること、結びつかなかった画像を消すこと。この規模では、書くときに各フォロワーへ配る処理が無い（ADR-0015）。`after()` は応答を返したあとに動くが、失敗してもやり直さない。

## 決定

- **新着と未読は、定期的な GET で確かめる。** TanStack Query の `refetchInterval`（30 秒）を使い、タブが見えていない間は止める
- WebSocket・Server-Sent Events・外のリアルタイムのサービスは使わない
- **通知の行は、元の操作（いいね・フォロー・返信など）と同じトランザクションで書く。** 元の操作が成功したのに通知が無い、という状態を作らない
- **無くなっても困らない処理だけを `after()` で行う**（表示の回数の加算、リンクの情報の取得など）
- 定期的な処理（結びつかなかった画像の掃除）は、ホストの cron から、秘密の値で守った Route Handler を 1 日に 1 回呼ぶ
- ジョブのキュー（pg-boss・Inngest など）は入れない
- ダイレクトメッセージを作るときに、Server-Sent Events と PostgreSQL の LISTEN / NOTIFY を使うかを、新しい ADR で決める

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 定期的な確認と、同じトランザクションと `after()`（採用） | 足すものが無い。どのホスティングでも動く。通知が欠けない | 最大 30 秒遅れる。確認のリクエストが定期的に来る |
| Server-Sent Events と LISTEN / NOTIFY | すぐ届く | 接続を保つ仕組みと、切れたときのつなぎ直しが要る。今の要件には過剰 |
| Pusher・Ably | 作るものが少ない | 外のサービスに頼る。ローカルで完結しない |
| 通知を `after()` で作る | 応答が少し速い | 失敗すると通知が欠け、やり直しが無い |
| pg-boss などのキュー | やり直しができる | 常に動く働き手が要る。今はやり直しが要る処理が無い |

## 結果

- 動くものは Next.js と PostgreSQL と S3 互換のストレージだけで済む
- 通知を作る分、元の操作のトランザクションが少し長くなる
- `after()` に入れてよいのは、無くなっても困らない処理だけ。入れる前にそれを確かめる
- 1 人が 30 秒ごとに 2 つの GET を送る。同時に 1,000 人が開いていると 1 秒に約 67 件で、索引を使う軽い問い合わせにする必要がある
