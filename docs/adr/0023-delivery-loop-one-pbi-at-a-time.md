# ADR-0023: EPIC の子 issue は、決まった手順のループで 1 件ずつ、閉じるまで終わらせる

- ステータス: 採用
- 日付: 2026-11-18
- 決定者: ユーザー（1 ループで完了させる・ハーネスを整える）／エージェント（手順）
- 関連: ADR-0003、ADR-0019、ADR-0020、ADR-0021、ADR-0022

## 背景

ユーザーは 2026-11-18 に「これを 1 ループで完了するように、SDLC のプロセスを全て再現した EPIC と sub-issue を作る」「ハーネスの整備が大事」と指示した。

エージェントが人の手を借りずにマイルストーンを終わらせるには、issue が単独で読めること（ADR-0003）に加えて、次に何をするか、どこで終わりとするか、前提が崩れたらどうするかが、会話ではなくリポジトリに書かれている必要がある。書かれていないと、セッションが替わるたびに進め方が変わり、確認を飛ばしたまま issue が閉じられる。

## 決定

- **EPIC の子 issue は、並んだ順に 1 件ずつ進める。** 開いていて、`blocked by` が全部閉じている最初の 1 件を取る
- **1 件の手順は固定する**: 最新の `main` と CI の確認 → issue と関係する ADR を読む → 変更の前の確認 → テストを先に書いて実装 → `pnpm verify` → 受け入れ条件を 1 つずつ確認 → 決定があれば ADR → commit と push → CI を最後まで見る → 根拠（commit・CI の実行・受け入れ条件ごとの確認の方法）を書いて閉じる
- 受け入れ条件を満たしていない・確認を飛ばした・CI が落ちている issue を閉じない
- 範囲の外の作業を混ぜない。見つけたものは、根本原因を書いた新しい PBI にする
- **issue の前提が崩れたとき**: ADR が代わりの手段を書いていればそれを使い、置き換えの ADR を書いて続ける。既存の ADR から 1 つに決まるなら、決めて ADR を書いて続ける。ユーザーの決定を覆す・範囲を変える・アカウントや秘密の値が要る場合だけ、その issue に根拠と勧める案を書いて `blocked` のラベルを付け、依存しない次の issue へ進む
- ループの終わりは、EPIC の子 issue が全部閉じたとき、または残りが全部 `blocked` のとき
- SDLC の工程（要件・設計・実装・テスト・リリース・運用と保守）を、マイルストーンの EPIC の下の子 EPIC として持つ。工程の順が、そのまま進める順になる
- 手順の細目は `.claude/rules/delivery-loop.md` に置く

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 1 件ずつ、閉じるまで（採用） | 途中で止まっても `main` が通った状態で残る。どこまで終わったかが issue で分かる | 並列にしないので、時間がかかる |
| 複数の PBI を並列のエージェントで進める | 速い | 最初のうちは骨組みと共通の部分を全員が触り、ぶつかる。`main` に直接 push する進め方と合わない |
| まとめて実装し、最後に確認する | 切り替えが少ない | 落ちたときに、どの変更が原因か分からない |
| 手順を EPIC の本文だけに書く | 1 か所で読める | EPIC ごとに書き写すことになり、ずれる |
| 前提が崩れたら必ず止まって聞く | 勝手に決めない | 1 ループで終わらない。ADR が答えを持っている場合まで止まる |

## 結果

- セッションが替わっても、issue の一覧と手順から続きを始められる
- 閉じた issue には、何で確かめたかが残る
- 並列にしない分、マイルストーン 1 は順番に進む。骨組みが落ち着いたあとで並列にするかは、新しい ADR で決める
- `blocked` の issue は、ループの最後の報告に、勧める案と一緒に出る
