# ADR-0029: ユーザーが PR を求めたマイルストーンは、1 本のブランチで進め、issue はマージで閉じる

- ステータス: 採用
- 日付: 2026-11-18
- 決定者: ユーザー（「issue 1 を全てやって PR を出す」）／エージェント（進め方の細目）
- 関連: ADR-0020、ADR-0023、ADR-0025、ADR-0028

## 背景

ADR-0020 と `.claude/rules/delivery-loop.md` は、PBI ごとに `main` へ直接 push し、`main` の CI で確かめ、issue を閉じると決めている。

ユーザーは 2026-11-18 に「issue 1 を全てやって PR を出して。私は寝る」と指示した。PR はユーザーが中身を見てからマージするためのもので、マージする前に `main` を変えると、その意味が無くなる。ユーザーは寝ていて、ループの途中で聞くことはできない（ADR-0028）。

CI は `main` への push と、全ての PR で動く（`.github/workflows/ci.yml`）。

## 決定

- **ユーザーが PR を求めたときは、作業を 1 本のブランチ（`m1/local-app`）に積む。** `main` へは push しない
- 最初の commit を push した時点で、**下書きの PR** を開く。以後、PBI ごとの push で PR の CI が動き、それを最後まで見る（ADR-0020 の「この変更の commit で CI が緑」は、PR の CI で満たす）
- PBI の手順は、push の先がブランチであることを除いて、全部そのまま（TDD・Chrome・独立したレビュー・試験レポート・バグは止めずに直す）
- **issue は、PR のマージで閉じる。** PBI ごとに、完了の定義にチェックを入れ、根拠のコメント（commit・CI の実行・試験レポート）を書く。閉じるのは、PR の本文の `Closes #N` に任せる。マージはユーザーが決める
- `v0.1.0` のタグは、マージされる前の commit に打たない。リリースは **下書き** として用意し、ユーザーがマージのあとで公開する（#36）
- マイルストーンを閉じるのも、マージのあと（#39）
- 全部の PBI を終えたら、下書きを外して、レビューできる状態にする

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 1 本のブランチ、マージで閉じる（採用） | ユーザーの指示どおり。マージの前に全体を見られる。`main` が変わらない | issue が開いたまま進む。PR が大きい |
| PBI ごとに PR を作る | 1 つずつ見やすい | 32 本の PR が積み重なり、前の PR に頼る。ユーザーは寝ていて、1 本ずつはマージできない |
| これまでどおり `main` に push し、最後に PR を作る | 手順が変わらない | PR に差分が無くなる。指示に反する |
| ブランチで進め、PBI ごとに issue を閉じる | 進み具合が issue で分かる | マージされていない変更で issue が閉じる |

## 結果

- PR が 1 本で大きくなる。PR の本文に、PBI ごとの commit と試験レポートの一覧を載せ、読む順を示す
- 進み具合は、各 issue の根拠のコメントと、完了の定義のチェックで分かる
- ユーザーが PR を求めないときは、これまでどおり `main` に push する（ADR-0020）
