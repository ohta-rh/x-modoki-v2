# 負荷の下で要求が返らない原因（#55）

## 調査日: 2026-11-19

## 1. 形

- `pnpm verify` の画面のテストを並べて流すと、ときどき 1 本の要求が返らない。テストは 5 秒や 90 秒で時間切れになる
- 2026-11-18 の記録（#55 の本文）: 投稿のあとの `GET /api/timeline/following?cursor=` に応答が無い（状態 -1）
- 2026-11-19 に、全部の実行を 26 回流して、この形を 3 回捕まえた
  - `GET /api/timeline/following?cursor=` が 7 秒
  - `GET /{username}/with_replies` が 77 秒
  - 同じページが 29.5 秒
  - どれも、応答の無いままブラウザに切られた

## 2. 調べ方

使い捨てのコードで、アプリのコードは変えていない。

- **中継**: 3300 番で受けて、アプリ（3310 番）へ渡す。要求ごとの始まり・終わり・時間と、5 秒を超えて開いているものを記録した
- **アプリの中の見張り**: `NODE_OPTIONS=--require` で読ませた
  - イベントループの遅れと、libuv のスレッドプールの遅れ（`fs.stat` の往復）を、0.1 秒ごとに測った
  - アプリが受け取った要求の時間を記録した
  - `pg` の問い合わせとプールの待ちを記録した。プールの待ちが 1 秒を超えたら、各接続が何を流しているかを書き出した
- **データベース**: `pg_stat_activity` の状態と待ちを、1 秒ごとに記録した

## 3. 分かったこと

| 疑ったもの | 結果 |
|---|---|
| データベースの遅い問い合わせ・鍵の待ち | 止まったあいだ、1 秒を超えた問い合わせは 0 本、待ち（`wait_event`）も無い |
| Node のイベントループの詰まり | 0.3 秒を超えた遅れは 0 回 |
| スレッドプール（パスワードの scrypt、ファイル、名前の引き） | 0.3 秒を超えた遅れは 0 回。32 件の scrypt で 0.4 秒待つことは確かめたが、止まった時刻には起きていない |
| macOS の接続を受ける待ち行列の溢れ | `listen queue overflow` は 0 |
| **プールの接続** | 止まった要求のプールは、接続 1 本が「つながる途中」のまま（`total=1 idle=0`、問い合わせは無し）。要求はそこで待ち続けた |

その接続の口を、アプリなしで試した（`127.0.0.1:54320`、OrbStack が公開した口）。

| 試し | 結果 |
|---|---|
| TCP の接続だけ 4000 本（50 本ずつ） | 最大 13ms |
| PostgreSQL のログインまで 3000 本（50 本ずつ） | 最大 1010ms、99 パーセンタイル 215ms |
| 同じく 150 本ずつ | 最大 1016ms、**99 パーセンタイル 1007ms** |

- 遅れは 1 秒の単位に固まっている。TCP の最初の合図（SYN）が落ちて送り直されるときの形で、送り直しの間は 1・2・4・8・16 秒と延びる
- 5 回落ちると合計は 31 秒で、見張りが捕まえた 29.5 秒と合う
- TCP だけなら OrbStack の口がその場で受けるので遅れない。遅れは、その奥の PostgreSQL へつなぐところで起きている
- アプリは要求ごとに新しいプールと接続を作る（ADR-0037、ADR-0050）。だから画面のテストを並べると、毎秒たくさんの新しい接続がこの口を通る

## 4. 根本原因

接続が一度にたくさん来ると、OrbStack が公開している PostgreSQL の口の奥で接続が秒の単位で遅れ、まれに何十秒もつながらない。そして `getDb()` のプールは、つなぐ時間に上限（`connectionTimeoutMillis`、決まりでは無し）を置いていないので、その要求も同じだけ止まる。

## 5. 推奨

- プールにつなぐ時間の上限を置き、上限を超えたら 1 回だけつなぎ直す。遅れの多くは 1 秒の送り直しなので、上限を少し超えたところでつなぎ直せば、ほとんどは次の 1 回で通る（決定は ADR-0057）
- 本番は Hyperdrive が接続をまとめる（ADR-0017）。この口は手元と CI の Docker だけの経路だが、上限の無い待ちは本番でも避けたい
