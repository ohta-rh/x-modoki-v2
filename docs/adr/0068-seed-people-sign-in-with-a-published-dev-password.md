# ADR-0068: シードの人は、公開した開発用のパスワードでログインできる

- ステータス: 採用
- 日付: 2026-11-19
- 決定者: エージェント（委任された判断。ADR-0028 によりユーザーに聞かずに決めた）
- 関連: #35、#16、ADR-0007

## 背景

- #35 の受け入れ条件は「まっさらな clone で手順書のコマンドを流すと、シードのユーザーで入れる」
- `scripts/seed.ts`（#16）は `users` の行だけを作り、Better Auth のパスワードの行（`accounts` の `providerId: 'credential'`）を作っていなかったので、シードの人では入れなかった（`scripts/seed.ts:24`、2026-11-19）
- シードはローカルの開発用で、データは全部架空（`sample01`〜`sample20`、`@example.test`）。本番にシードは流さない

## 決定

- シードの 20 人それぞれに `providerId: 'credential'`、`accountId` が人の ID の `accounts` の行を作る
- パスワードは全員 `sample-password`（`SEED_PASSWORD`）。手順書と README に書いて公開する
- ハッシュは Better Auth と同じ `better-auth/crypto` の `hashPassword` で 1 回だけ作り、20 人で使い回す

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **決まった値を公開する（採用）** | 手順書を読むだけで入れる。CI でも同じ値で確かめられる | 値は秘密ではない（開発用の架空の人だけなので害は無い） |
| 乱数で作り、シードのときに表示する | 機械ごとに違う | 表示を見逃すと入れない。CI で確かめにくい |
| シードの人では入れないまま、新しく登録させる | シードを変えない | 投稿とフォローのある人として画面を見られない |
| 人ごとにハッシュを作る | 行ごとに塩が違う | 20 回の scrypt で数秒かかる。開発用の決まった値には意味が無い |

## 結果

- 良くなること: clone して手順書どおりに流せば、投稿とフォローのある人として画面を確かめられる
- 受け入れる負担: パスワードが誰にでも分かる。シードを本番のデータベースに流してはいけない
- 守ること: シードを本番に向けない。シードの人を足すときは `accounts` の行も足す
