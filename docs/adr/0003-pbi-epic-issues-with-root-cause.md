# ADR-0003: 作業は PBI 型の EPIC と子 issue で計画し、起票の前に根本原因を特定する

- ステータス: 採用
- 日付: 2026-11-18
- 決定者: ユーザー
- 関連: ADR-0001

## 背景

issue を症状だけから書くと、症状に対する修正が入り、同じ問題が形を変えて戻る。実装を始めてから決めていないことが見つかると、issue を書き直して作業をやり直すことになる。

ユーザーは 2026-11-18 に「PBI 型で EPIC と issue を作る」「issue を作るときは必ず root cause を特定し、手戻りのない issue を書く」と指示した。

## 決定

- **計画する作業は、EPIC の issue 1 つと、その子の PBI の issue として書く。** EPIC はユーザーが名前で言える成果 1 つ。PBI は単独で価値が出て、単独で実装・検証・マージできる縦のスライス。層（backend 分・frontend 分）では分けない
- EPIC に属さない issue は作らない。合う EPIC が無ければ先に EPIC を作る
- **根本原因を一文で言えるまで、issue を起票しない。** 不具合は実データで再現してから原因までたどり、根拠（file:line・ログ・再現手順）を書く。機能の追加は「誰が、何に、なぜ困っているか」を根本原因とする
- 原因を特定できないときは、受け入れ条件を「根本原因を根拠つきで特定する」とした調査の PBI を起票する。推測の上に実装の PBI を書かない
- 起票の前に、実装する人が決めることになる事柄（データの形、公開インターフェースの名前、エラーの振る舞い、移行）を決めて本文に書く。未決の問いを本文に残さない
- 作業の計画はドキュメントにしない。`docs/` には今の設計と決定の理由だけを置く

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| EPIC と子の PBI（採用） | 成果の単位で進み具合が見える。PBI は単独でマージできるので、途中で止めても価値が残る | 起票の前の調査に時間がかかる |
| EPIC 無しの平らな issue | 起票が速い | 何のための issue かが issue ごとに散らばる。順番と依存が見えない |
| 層ごとのタスク（backend / frontend） | 担当を分けやすい | 片方だけでは動かず、検証できない。結合のときに食い違いが出る |
| 計画書を `docs/` に置く | 1 か所で全体が読める | issue と二重に持つことになり、ずれる |

## 結果

- issue を読めば、会話の履歴が無くても実装を始められる
- 起票の前に調査と決定を済ませるので、起票は遅くなる。その代わり実装の途中の書き直しが減る
- 運用の細目・チェックリスト・ひな形は `.claude/rules/issue-authoring.md` に置く
