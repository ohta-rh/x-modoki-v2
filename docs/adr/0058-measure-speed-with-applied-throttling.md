# ADR-0058: 画面の速さは、Lighthouse のモバイルの回線と CPU の条件を実際にかけて測り、3 回の中央の値で判定する

- ステータス: 採用
- 日付: 2026-11-19
- 決定者: エージェント（委任された判断。ADR-0028 によりユーザーに聞かずに決めた）
- 関連: #32、NFR-PERF-01〜03、[速さの調べ](../research/performance-m1.md)

## 背景

- NFR-PERF-01〜03 は「Lighthouse のモバイルの設定」で、5 つの画面の LCP 2.5 秒・CLS 0.1・TBT 200 ミリ秒を求める
- Lighthouse 13.6.0 の決まりの測り方は、条件をかけずに読み込み、モバイルの回線（往復 150ms、1.6Mbps）と 4 倍遅い CPU での値を見積もる（simulated）。2026-11-19 の手元の本番ビルドで測った
  - プロフィールと検索の LCP の見積もりは 3.2〜4.0 秒だった。実際に描かれた LCP は、どの回も 0.36〜0.45 秒だった
  - JavaScript の塊だけをふさいで測ると、見積もりは 1.4〜1.7 秒下がった
  - この画面は、本文を流して差し込む（Suspense）。差し込むのは HTML の中の小さなスクリプトで、あとから読む JavaScript を待たない。見積もりは、描かれた時刻より前に始まった通信を、全部 LCP の前に要るものとして数える
- 同じ回線と CPU の条件を実際にかけて測ると（`throttlingMethod: 'devtools'`）、5 つの画面の LCP は 1.3〜2.25 秒だった
- 条件を実際にかける測り方は、1 回ごとの揺れが大きい

## 決定

- **`scripts/perf.mjs` は、Lighthouse のモバイルの回線と CPU の条件を、そのまま実際にかけて測る**（`throttlingMethod: 'devtools'`。条件の値は Lighthouse の決まりのまま）
- **1 つの画面を 3 回測り、項目ごとに真ん中の値で予算と比べる**
- 速さの計測は手元で行い、CI には入れない（#32 のスコープのとおり、測るたびに揺れるため）

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **条件を実際にかけ、3 回の中央の値（採用）** | 差し込みの描画を、そのとおりに測る | 1 回ごとに揺れる。1 つの画面に約 1 分かかる |
| 決まりの見積もり（simulated） | 速く、揺れが小さい | 流して差し込む画面の LCP を 1.5 秒以上遅く見積もり、直すべき所を取り違える |
| 見積もりのまま、予算をゆるめる | 手間が無い | 要件を弱めることになる |
| 差し込みをやめ、画面を一度に返す | 見積もりと合う | 最初に何かが見えるまでが遅くなる。ADR-0021 の作りを崩す |

## 結果

- 良くなること: 測った値が、遅い回線と CPU の上で人が見る速さに近くなる。見積もりの誤りで、JavaScript の量の問題と描画の問題を取り違えない
- 受け入れる負担: 測るのに時間がかかる（5 つの画面で約 6 分）。値は 1 回ごとに揺れるので、際どい画面は測り直す
- 守ること: 調べの記録には、見積もりの値も並べて残す。最初に送る JavaScript の量は、この測り方とは別に e2e で確かめる（[ADR-0059](0059-load-popups-and-parsers-on-first-use.md)）
