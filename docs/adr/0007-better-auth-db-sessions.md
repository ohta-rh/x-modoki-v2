# ADR-0007: 認証は Better Auth を使い、セッションはデータベースに持つ

- ステータス: 採用
- 日付: 2026-11-18
- 決定者: エージェント（委任された判断）
- 関連: [バックエンド技術選定](../research/backend.md)、ADR-0006、ADR-0010

## 背景

ユーザー名とパスワードでの登録とログインが要る。外のサービスに頼らず、ローカルの Docker だけで全部が動くことが要る。

2026-11-18 に確認した事実: Auth.js（NextAuth）は 2025-09-22 に Better Auth のチームの管理に移り、新しいプロジェクトには Better Auth が公式に勧められている。`next-auth` の v5 は beta のままで正式版になっていない。Lucia は非推奨。`better-auth` の `latest` は 1.7.25。Better Auth が Next.js 16.4 で動くことは、実際には試していない。

## 決定

- **認証は Better Auth 1.7 系。** Drizzle のアダプターで、ADR-0006 の PostgreSQL に表を持つ
- **セッションはデータベースに持つ**（HttpOnly の cookie にセッションのトークン）。JWT だけのセッションは使わない
- 最初に作るのは、ユーザー名・メールアドレス・パスワードでの登録とログイン、ログアウト。`username` のプラグインで @handle を持つ
- メールの確認、Google と GitHub でのログイン、パスキーは後の段階で足す。足すときにライブラリを替えなくてよい
- ハンドラーは `app/api/auth/[...all]/route.ts`。サーバー側でセッションを読む関数はデータアクセス層に 1 つだけ置き、React の `cache()` で同じリクエストの中では 1 回だけ読む
- ログインと登録への回数の制限は、Better Auth の組み込みのもの（データベースに記録）を使う

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| Better Auth（採用） | 新しいプロジェクトに公式に勧められている。ローカルで完結。ユーザー名・OAuth・パスキーを同じライブラリで足せる | Next.js 16.4 での動作を試していない |
| Auth.js v5 | 利用の例が多い | beta のままで、保守だけの状態。パスワードでのログインに制約がある |
| Clerk | 作るものが最も少ない | 外のサービスに頼る。ローカルの Docker だけで動かない。ユーザーのデータが外にある |
| 自分で作る | 依存が無い | パスワードのハッシュ・回数の制限・メールの確認を全部作ることになり、間違えやすい |
| JWT だけのセッション | データベースを読まずに済む | ログアウトや無効化をすぐに効かせられない |

## 結果

- ユーザーとセッションは自分のデータベースにある。ログアウトとセッションの無効化はすぐ効く
- リクエストごとにセッションの行を 1 回読む。この規模では問題にならない
- 最初の EPIC で、Better Auth が Next.js 16.4 の `proxy.ts` と Server Action で動くことを確かめる。動かなければ、この ADR を置き換える
- ユーザーの表は Better Auth が決める形（ID は文字列）に従い、プロフィールの列はそこに足す
