# ADR-0036: 登録とログインの回数の制限は、IP ごとに 1 分 10 回を既定にし、画面のテストのサーバーだけ環境変数で上げる

- ステータス: 採用
- 日付: 2026-11-18
- 決定者: エージェント（委任された判断。ADR-0028 によりユーザーに聞かずに決めた）
- 関連: ADR-0010、ADR-0024、NFR-SEC-05、[脅威の洗い出し](../architecture/threat-model.md) の T-10、#18

## 背景

NFR-SEC-05 は、ログインと登録を同じ IP から 1 分に 10 回までにすると決めている。数えるのは `rate_limits` の表（ADR-0010）。

Playwright の画面のテストは、3 つのブラウザから並列に動き、ログインした状態を作るためにテストごとに登録する。全てが `127.0.0.1` から来るので、1 分に数十回の登録になり、10 回の制限に当たって落ちる。

IP を `X-Forwarded-For` から読むと、テストごとに違う値を送って制限を分けられるが、その値は利用者が自由に書けるので、本番で制限を回り込まれる。

## 決定

- **登録とログインは、1 つの予算を IP ごとに数える**（キー `auth:<IP>`、1 分の区切り）。IP は Cloudflare が付ける `cf-connecting-ip`、無ければ `x-forwarded-for` の先頭、無ければ `unknown`
- **1 分の回数は `AUTH_RATE_LIMIT_PER_MINUTE` で変えられる。既定は 10。** `src/shared/config/env.ts` が正の整数として読む
- **Playwright のサーバー（`playwright.config.ts` の `webServer.env`）だけ 1000 にする。** 本番と手元の `pnpm start` は既定の 10
- 10 回で止まることは、Vitest のデータアクセス層のテスト（既定の値）で確かめる

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 回数を環境変数にし、画面のテストのサーバーだけ上げる（採用） | 本番の制限が変わらない。テストの側に細工が要らない | 画面のテストでは制限そのものを確かめない（Vitest で確かめる） |
| `X-Forwarded-For` をテストごとに変える | 制限を残したまま画面のテストが動く | 利用者がこの値を書けば、本番で制限を回り込める |
| 画面のテストでは登録をやめ、シードの人で入る | 登録の回数が減る | 並列のテストが同じ人を使い、互いのデータが混ざる |
| 画面のテストを 1 つずつ順に動かす | 制限を変えない | 1 分に 10 回でも足りず、遅い |

## 結果

- `AUTH_RATE_LIMIT_PER_MINUTE` は `.env.example` に書かない（既定で 10）。[環境と配備](../architecture/environments.md) の 3 節に書く
- 本番で値を変えるときは、この ADR を置き換える
