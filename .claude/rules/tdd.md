# Test-driven development — always

Applies to every change to executable code in this repository (ADR-0026). It is item 2 of the
Definition of Done (`.claude/rules/definition-of-done.md`): work that was not test-driven is
not done, however green it is.

If the `superpowers:test-driven-development` skill is available, load it before implementing;
where it and this file differ, this file wins.

## The cycle — one behavior at a time

1. **Red.** Write one test for one behavior. Run it. **Watch it fail for the expected reason**
   — the behavior is missing. A syntax error, a failed import, or a typo in the test is not red;
   fix the test until it fails because the behavior does not exist.
2. **Green.** Write the smallest production code that makes that test pass. Run the whole
   suite; everything passes.
3. **Refactor.** With the suite green, remove duplication and fix names. Run it again.

Then the next behavior. Do not write the next test while one is red, and do not write
several tests ahead.

## Hard rules

- **No production code without a failing test that demands it.** If you wrote code first,
  delete it and start from the test — do not keep it and back-fill a test that passes.
- **Never write a test you have not seen fail.** A test that passes the first time it runs
  proves nothing; make it fail (assert the opposite, remove the code) before trusting it.
- **A bug fix starts with a test that reproduces the bug and fails.** Then fix.
- **One reason to fail per test.** Name the test after the behavior
  (`likePost — 他人のセッションでは FORBIDDEN を返す`), not after the function.
- **Work outside-in for anything a user can see.** First the Playwright test for the
  acceptance criterion, failing. Inside it, drive each unit and data-access function
  red → green. The Playwright test goes green last.
- **Do not change a test to make it pass** unless the test was wrong; say why in the report.
- Refactoring changes no behavior, so it adds no test — but it never happens on red.
- Tests exercise the real PostgreSQL for `api` segments (ADR-0013). Mock only time,
  randomness, and storage signing.

## What it covers

| Covered — test first | Not covered |
|---|---|
| Everything under `src/` | Config files (`*.config.*`, `tsconfig.json`, CI YAML) |
| `app/api/**/route.ts`, `proxy.ts` | SQL generated by `drizzle-kit` |
| `scripts/` | `src/shared/ui/kit/` (vendored shadcn/ui) |
| Helpers under `e2e/` | `src/shared/db/schema/` (declarations) and type-only files |
| | Throwaway investigation code outside the repository |

`app/**/{page,layout,default,not-found,error,global-error}.tsx` cannot be unit-tested (ADR-0021, ADR-0039, ADR-0062): write the Playwright test
for the route first and watch it fail, then add the route file.

Adding to the "not covered" column requires a new ADR.

## The record — no record, no TDD

Every test report for a PBI that changes code has a `### TDD の記録` subsection under
`## 自動のテスト` (ADR-0025), one row per behavior, written as you go — not reconstructed
afterwards:

```markdown
### TDD の記録
| # | 振る舞い | 先に書いたテスト | 赤（落ちた理由） | 緑にした実装 |
|---|---|---|---|---|
| 1 | 281 の重みの本文は投稿できない | `count-weight.test.ts` › 281 は超過 | `expected false, received undefined` — `isOverLimit` が無い | `src/shared/lib/text/weight.ts` |
```

- The 赤 column quotes the actual assertion message from the failing run.
- A PBI with no code change writes `コードの変更なし` in place of the table.
- `check-docs.mjs` rejects an `issue-NNNN-*` test report that has no `### TDD の記録`.

## When TDD feels impossible

- *"I don't know the API yet."* Spike in a throwaway directory, learn it, delete the spike,
  then start from a test.
- *"It's only wiring."* Then the Playwright test is the failing test. Write it first.
- *"The test is hard to write."* That is design feedback: the code needs a seam. Change the
  design, not the rule.
- *"It's a one-line fix."* A one-line test first.
