# ADR-0056: PBI の中で見つけたバグはその PBI の中で直し、バグの issue は探索的テストの分だけにし、手元の全部の確認は push の前に 1 回にする

- ステータス: 採用
- 日付: 2026-11-19
- 決定者: ユーザー（「中で見つけたバグは中で直す」「手元は関係する e2e だけ」「バグ issue は探索的テストで見つかったものだけでいい」）
- 関連: [ADR-0028](0028-bugs-are-fixed-to-completion-without-asking.md)（範囲の外のバグを、バグの PBI にしてすぐ直す決まりを、この ADR で置き換え）、ADR-0024、ADR-0025、ADR-0027

## 背景

- 2026-11-19、ユーザーは「この開発プロセスの実行速度が遅すぎる」と指摘した
- その日の時間の使い方:
  - `pnpm verify` の全部を 15 回ほど流した。1 回 10〜12 分
  - 作り直しを 30 回ほどした。1 回 2 分
  - CI を 8 回ほど待った。1 回 15 分
- #30 の中で見つけたバグ 5 件（#60〜#64）は、ADR-0028 に従い、1 件ずつ別の PBI にした。どれも、Chrome の確認・独立したレビュー・試験レポート・CI を丸ごと回した
- ユーザーは次を選んだ
  - まず #55 を直す
  - 作業中の手元の確認は、関係する e2e だけにする
  - 中で見つけたバグは中で直す
  - バグの issue は、探索的テストで見つかったものだけでいい

## 決定

- **PBI の作業の中で見つけたバグは、範囲の中でも外でも、今の PBI の中で直す。** 直し方は、今の PBI の commit と同じ。落ちるテストを先に書き、独立したレビューを通し、`pnpm verify` と CI を緑にする。記録は、今の PBI の試験レポートの「見つけた問題」に書く。別の issue・試験レポート・完了の定義は作らない
- **バグの issue は、探索的テスト（#34 など）で見つけたものだけに起こす。** 起こすときの形は `.claude/rules/issue-authoring.md` の決まりどおり
- **作業中の手元の確認は、変えたものに関係する単体のテストと e2e の spec だけにする。** `pnpm verify` の 7 つの確認の全部は、push の直前に 1 回流す（rebase のあとはもう一度）。完了の定義の「`pnpm verify` が 0 で終わった」と、CI で全部を流すことは変えない
- ADR-0028 のほかの決まりは、そのまま守る
  - 見つけたバグは最後まで直す
  - 重さで先送りしない
  - ループを止めない
  - ユーザーに聞かない
  - 確認を弱めない

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **中で直す・issue は探索的テストの分だけ・手元の全部は push の前に 1 回（採用、ユーザーが選んだ）** | PBI ごとの CI の待ちと確認が減る。バグはその場で直る | バグの記録が試験レポートに分かれ、issue の一覧では追えない |
| 今のまま（ADR-0028） | バグごとに issue と試験レポートが残る | 小さな直しでも、完了の定義を丸ごと回す |
| 試験レポートを変更と同じ commit に入れる | CI の待ちが PBI ごとに 1 回減る | ユーザーは選ばなかった（ADR-0025 のまま） |

## 結果

- 良くなること: PBI ごとの手元の確認と CI の待ちが減る
- 受け入れる負担: PBI の中で見つけたバグは、その PBI の試験レポートを読まないと見つからない
- 守ること: 中で直したバグも、落ちるテストを先に書き、レビューと CI を通す。push の前の `pnpm verify` は省かない
