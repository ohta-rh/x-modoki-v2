# ADR-0015: タイムラインは読むときに組み立て、いいねなどの数は投稿の行に持つ

- ステータス: 採用
- 日付: 2026-11-18
- 決定者: エージェント（委任された判断）
- 関連: [バックエンド技術選定](../research/backend.md)、[データモデル](../architecture/data-model.md)、ADR-0006、ADR-0011

## 背景

タイムラインには「フォロー中」と「おすすめ」がある。規模は数十人から数千人で、1 人がフォローする数も多くて数千。投稿カードは、いいね・リポスト・返信の数を毎回出す。

タイムラインの作り方には、書くときに各フォロワーの表へ配るやり方と、読むときにフォローの表と投稿の表を結合するやり方がある。配るやり方は、配る処理を応答のあとで動かす仕組みと、失敗したときのやり直しが要る。

## 決定

- **「フォロー中」は、読むときに組み立てる。** 自分とフォローしている人の投稿を、投稿の ID の降順で取る。書くときに各フォロワーへ配る表は作らない
- **「おすすめ」は、全員の投稿（返信を除く）を新しい順に出す。** 点数での並べ替えは作らない
- ページングは、投稿の ID をカーソルにする（`id < カーソル` で次の 20 件）。`OFFSET` は使わない
- リポストは、`posts` の 1 行（元の投稿の ID を持ち、本文が無い）として持つ。タイムラインの問い合わせは 1 つの表を読むだけで済む
- **いいね・リポスト・返信・引用・ブックマークの数は、`posts` の列に持つ。** いいねなどの行の追加・削除と同じトランザクションで、`SET like_count = like_count + 1` の形で増減する
- 自分がいいねしたか・リポストしたか・ブックマークしたかは、一覧を取る問い合わせの中でまとめて引く。投稿ごとに問い合わせない

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 読むときに組み立てる（採用） | 仕組みが要らない。フォローやブロックの変更がすぐ反映される | フォローする数が数万になると、結合が重くなる |
| 書くときに配る | 読むのが速い | 配る処理・やり直し・フォローを外したときの掃除が要る |
| 数を毎回 `COUNT` で数える | 数がずれない | 投稿カードごとに集計が走る |
| 数を応答のあとで更新する | 元の操作が速い | 失敗すると数がずれ、直す仕組みが要る |
| 「おすすめ」を点数で並べる | X に近い | 点数の順でのページングは、途中で順が変わる。学習用には過剰 |
| リポストを別の表に持つ | 投稿の表が単純 | タイムラインで 2 つの表を合わせて並べ直すことになる |

## 結果

- 動く仕組みが増えない（ADR-0011）
- `posts(author_id, id)` と `follows(follower_id)` の索引が要る
- 同じ投稿に同時にいいねが集まると、その行の更新が順番待ちになる。この規模では問題にならない
- 「おすすめ」は X の並びとは違う。点数での並べ替えを入れるときは、新しい ADR で決める
