# ADR-0060: 全ての入口に、印の付いた認可のテストを求め、lint で突き合わせる

- ステータス: 採用
- 日付: 2026-11-19
- 決定者: エージェント（委任された判断。ADR-0028 によりユーザーに聞かずに決めた）
- 関連: #33、NFR-SEC-01、[脅威の洗い出し](../architecture/threat-model.md)、ADR-0010

## 背景

- 認可のテストは変更の関数ごとに書かれていたが、全部の入口に対して抜けが無いかは、通しで見ないと分からなかった（#33 の根本原因）
- 2026-11-19 に名前で探すと、Server Action 4 つ（`createPostAction` の返信と引用・`setPinAction` ほか）と Route Handler 2 つに「ログイン無しは拒む」のテストが無かった
- 調べる途中で、ログインが要る画面の検索の API（`/api/search`）と未読の数の API が、ログイン無しでも 200 を返していた。画像の署名の API は、別のサイトの `Origin` の POST に署名していた（T-11 の対策が抜けていた）
- 名前で探す方法は、テストの言い回しが変わると外れる

## 決定

- **全ての入口に、印の付いたテストを求める。** テストの直前に `// AUTHZ: <関数> <種類>` を書く（重ねてよい）
  - Server Action（`src/features/*/api/actions.ts` の export）と Route Handler（`src/_app/api-routes/*.ts` の export）は `UNAUTHORIZED`
  - 変更の関数（ほかの `src/features/*/api/*.ts` の export）は `UNAUTHORIZED` と、`FORBIDDEN`（他人の物を名指せる関数）か `SELF`（セッションの利用者の行しか変えられないことを、作者とは別の人で確かめる）
- **ログインの要らない入口は、脅威の文書の 6 節に、理由と一緒に載せる。** 載っていない入口は全部求める
- **脅威の表の「確かめるテスト」は、`` `パス` › テストの名前 `` で書く。** 受け入れた脅威だけ `—`
- `node scripts/check-authz.mjs` がこれら全部を確かめ、`pnpm lint` の中で動く（CI の 3 番目の確認）
- ログインが要る画面のデータは、`proxy.ts` だけでなく、データアクセス層でも拒む（ADR-0010 のとおり。検索と未読の数を直した）

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **印のテストと、lint での突き合わせ（採用）** | 抜けが lint で止まる。言い回しに左右されない | 新しい入口を足すたびに印を書く手間 |
| テストの名前の言葉で探す | 印が要らない | 言い回しの違いで外れ、偽の合格を出す |
| 入口ごとの一覧を手で保つ | 単純 | 新しい入口を足したときに更新を忘れる |
| 全部の入口を 1 つの共通の包みで守る | 書き忘れが無い | 今の作り（関数ごとの確認、ADR-0010）を全部書き換える |

## 結果

- 良くなること: 全部の入口（2026-11-19 で 34、ログイン不要 14）の認可がテストで確かめられ、新しい入口に印が無ければ lint で止まる
- 受け入れる負担: 入口を足すときに、印のテストか、6 節の理由の行が要る
- 守ること: 印は、その振る舞いを本当に確かめているテストにだけ付ける。`SELF` のテストは、作者とセッションの利用者を別の人にする（同じ人だと区別できない）
