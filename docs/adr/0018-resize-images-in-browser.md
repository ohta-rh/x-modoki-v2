# ADR-0018: 画像の縮小と変換は送る前にブラウザで行い、サーバーでは変換しない

- ステータス: 採用（WebP にできないブラウザの扱いを ADR-0043 で置き換え）
- 日付: 2026-11-18
- 決定者: エージェント（委任された判断）
- 関連: [Cloudflare Workers で動かす方法の調査](../research/cloudflare.md)、ADR-0008（画像の変換の節をこの ADR で置き換え）、ADR-0017

## 背景

ADR-0008 は、投稿に結びつけるときに、サーバーで `sharp` を使って決まった幅の WebP を作ると決めていた。本番が Cloudflare Workers になり（ADR-0017）、ネイティブのモジュールである `sharp` は動かない。

Cloudflare Images の変換は、R2 の画像に使えて、月に 5,000 種類まで無料。ただし、ローカルの S3 互換のストレージには同じ仕組みが無く、ローカルと本番で画像の出し方が変わる。

ブラウザは、`createImageBitmap` と `OffscreenCanvas` で画像を縮小し、WebP に書き出せる。

## 決定

- **画像は、送る前にブラウザで変換する。** 長辺を 2048px 以下に縮め、WebP（品質 0.85）にする。アバターは 400×400、バナーは 1500×500 に切り抜く。GIF はそのまま送る
- 変換のときに、位置の情報などのメタデータは落ちる（Canvas を通るため）
- **サーバーでは画像を変換しない。** `sharp` は入れない
- サーバー（署名つき URL を出す Route Handler と、投稿に結びつける Server Action）が確かめるのは次のこと
  - 種類が `image/webp`・`image/gif` のどちらか
  - 大きさが 5MB 以下（署名に大きさの範囲を入れる）
  - 結びつけるときに、置かれたものの先頭の数バイトを読み、種類が申告と合うこと
  - 幅と高さ（ブラウザが申告した値を、先頭のバイトから読んだ値で確かめる）
- 表示は、置いた 1 つの画像を `<img>` で出す。幅と高さを付けて、読み込みで配置がずれないようにする。`srcset` は使わない
- `next/image` の最適化は使わない（ADR-0008 のまま）
- 画像は、アプリとは別のドメイン（R2 の公開のドメイン）から出す

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| ブラウザで変換する（採用） | ローカルと本番で同じ。サーバーの CPU を使わない。送る量が減る。Workers の制約に当たらない | ブラウザを通さずに送られたものは変換されていない。幅ごとの画像が無いので、小さい画面にも同じ画像を送る |
| Cloudflare Images の変換 | 幅ごとに最適な画像を出せる | ローカルに同じ仕組みが無い。5,000 種類を超えると料金がかかる |
| Workers で WASM の変換（`@jsquash` など） | サーバーで作り直せる | CPU の時間とメモリ（128MB）に当たりやすい |
| 変換しない | 作るものが無い | スマートフォンの写真（数 MB）をそのまま配ることになる |
| `sharp`（ADR-0008） | 質が高い | Workers で動かない |

## 結果

- 画像の処理が、どの環境でも同じコードになる
- 変換を通さずに送る人がいても、種類・大きさ・先頭のバイトの確認で、画像でないものと大きすぎるものは弾ける。画像は別のドメインから出すので、アプリの cookie は付かない
- 幅ごとの画像が要るほど利用が増えたら、Cloudflare Images の変換を足す ADR を書く
- ブラウザでの変換は純粋な関数（`src/features/media/`）にして、単体のテストで確かめる
