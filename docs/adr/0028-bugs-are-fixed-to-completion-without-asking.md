# ADR-0028: 見つけたバグは、ループを止めず、ユーザーに確認を求めずに、その場で最後まで直し切る

- ステータス: 採用（範囲の外のバグをバグの PBI にする決まりを ADR-0056 で置き換え）
- 日付: 2026-11-18
- 決定者: ユーザー（バグは自動で修正まで全てやり切る。ループは止めない。ユーザーへの確認を求めない）／エージェント（手順）
- 関連: ADR-0003、ADR-0023（前提が崩れたときの扱いと `blocked` をこの ADR で置き換え）、ADR-0024、ADR-0025、ADR-0026、ADR-0027（3 回で `blocked` にする決まりをこの ADR で置き換え）

## 背景

ユーザーは 2026-11-18 に「バグがあった場合、自動で修正まで全てやり切るルールにする。ループは止めない。ユーザーへの確認を求めない」と指示した。

これまでの決定には、ループが手を止める・先へ送る場所が 4 つあった。

- 範囲の外のバグは、PBI にするだけで直さない（ADR-0023、完了の定義）
- 直し方が争われるときは、`blocked` のラベルを付けてユーザーの判断を待つ（ADR-0023）
- コードレビューが 3 回で承認にならなければ、`blocked` にする（ADR-0027）
- 探索的テストで見つけた中と低の不具合は、開いたままの PBI にする（#34 の受け入れ条件）

どれも、バグが残ったままループが先へ進むか、人を待って止まる。マイルストーンを 1 回のループで終わらせる（ADR-0023）ことと両立しない。同じ日に、機械の確認が通っていた issue の表示の崩れ、切れた写真、ドキュメントの確認の欠け 14 件、Node.js の版の違いによる CI の失敗を、全部その場で直している。止まって聞く必要があったものは 1 つも無かった。

## 決定

### バグは、見つけたときに、最後まで直す

- **バグを見つけたら、どこで・誰が見つけたものでも、ループの中で最後まで直す。** 見つける場所は問わない（テスト・`pnpm verify`・CI・Chrome での確認・コードレビュー・探索的テスト・前に閉じた PBI の退行）
- 「最後まで」とは、再現する → 根本原因を 1 文で言う → 再現して落ちるテストを書く → 直す → `pnpm verify` → Chrome で確かめる → コードレビューで承認 → push → CI が緑 → 試験レポートに書く、まで
- **重さで先送りしない。** 重大・高・中・低のどれも直す。「既知の不具合」として残さない
- **範囲で先送りしない。** 今の PBI の範囲の中のバグは、その PBI の中で直す。範囲の外のバグ（前に閉じた PBI のコード、関係の無い場所）は、根本原因を書いたバグの PBI を起票し、**今の PBI を続ける前に、すぐ直して閉じる**。起票するのは記録のためで、あとに回すためではない
- `main` の CI が落ちたら、ほかの全部より先に直す。すぐ直せなければ、その commit を取り消してから直す

### ループは止めない

- **`blocked` のラベルを、バグには使わない。** バグを理由に、PBI を飛ばさない・ループを終えない
- 直すのに失敗したら、同じことを繰り返さず、段を上げる
  1. 再現と根本原因に戻る（推測で直さない）
  2. 同じバグに 3 回失敗したら、当て布をやめる。最後に緑だった状態に戻し、設計を疑う。ADR が代わりの手段を書いていればそれを使い、無ければ別の作り方を選び、置き換えの ADR を書く
  3. それでも直らなければ、変更を小さく分け直して、1 つずつ TDD でやり直す
- コードレビューが 3 回で承認にならないときも同じ。4 回目を同じ形で出さず、最後に緑だった状態に戻して、小さく分けてやり直す。承認が出るまで続ける
- 確認を弱めて通さない。落ちるテストを消さない・飛ばさない・カバレッジから外さない・リンターを止めない（ADR-0020、ADR-0021）。これは「直した」に数えない

### ユーザーに確認を求めない

- **ループの中で、ユーザーに質問しない。** 「どちらにしますか」「進めてよいですか」を聞かない。選択肢を並べて待たない
- 判断が要るときは、既存の ADR とルールから決める。そこに答えが無ければ、エージェントが決め、**同じ commit で ADR を書く**（決定者はエージェント）。ユーザーは、あとから置き換えの ADR で覆せる
- 決めたことは、ループの最後の報告に全部並べる
- **聞かないことは、してよいことを増やさない。** 次のことは、聞かずにやるのではなく、やらない。別の道を探す
  - 強制の push、履歴の書き換え、自分が作っていないものの削除
  - 料金のかかる契約、外のサービスのアカウントの作成、秘密の値の入力
  - issue が許していない、外への公開
  - 確認を弱めること
- マイルストーン 1 は、アカウントも料金も秘密の値も要らない（ADR-0019）。だから、上の理由で直せないバグは、マイルストーン 1 には無い。もし当たったら、それを要らない作り方に替え、ADR を書いて続ける

### 記録

- バグごとに、試験レポートの「見つけた問題」に、見つけ方・根本原因・落ちるテスト・直した commit を書く（ADR-0025）
- 範囲の外のバグは、バグの PBI（ラベルは `bug` と `pbi`）としても残し、直した commit と試験レポートを付けて閉じる
- 同じ種類のバグが 2 回出たら、機械で防ぐ（リンターの決まり・スクリプトの確認・テスト）か、ルールに足す

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 見つけたらその場で最後まで直す。止めない・聞かない（採用） | バグが積もらない。1 回のループで終わる。原因の変更に近いうちに直せる | 1 つのバグに時間を使うことがある。エージェントの決定が増える（ADR で残す） |
| 範囲の外は PBI にして、あとで直す（これまで） | 今の PBI が速く閉じる | バグが残ったまま先へ進む。あとで直すと、原因から遠い |
| 重大と高だけ直し、中と低は残す | 時間を守れる | 「既知の不具合」が積もる。どこまでが中かで迷う |
| 争われる直し方は `blocked` にして待つ（これまで） | ユーザーが決められる | ループが人を待つ。ユーザーの指示に反する |
| 聞かずに、何でも実行する | 止まらない | 取り返しのつかない操作と、料金のかかる操作まで含んでしまう |
| 失敗の回数に上限を付けて、超えたら止める | 無限に回らない | 止まる。上限の代わりに、3 回ごとに作り方を変えることで防ぐ |

## 結果

- マイルストーンが終わったとき、開いたままのバグが無い
- ループは、人を待つ状態を持たない。終わるのは、EPIC の子 issue が全部閉じたときだけ
- エージェントが決める場面が増える。その全部が ADR に残り、最後の報告に並ぶ
- 1 つのバグに長くかかることがある。3 回ごとに作り方を変える決まりで、同じ失敗の繰り返しを防ぐ
- ユーザーが途中で指示を出したら、それに従う。この ADR が禁じているのは、ループの側から聞くことだけ
