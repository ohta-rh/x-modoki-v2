# ADR-0070: CI の確認を 8 つにし、本番の依存の監査を最初に動かす

- ステータス: 採用
- 日付: 2026-11-20
- 決定者: エージェント（委任された判断。ADR-0028 によりユーザーに聞かずに決めた。CI を必須とすることはユーザーの決定のまま）
- 関連: #37、#33（T-18、NFR-SEC-11）、ADR-0020（置き換える）、ADR-0033、ADR-0046、ADR-0047、ADR-0069、ADR-0071

## 背景

- ADR-0020 は、CI の確認を 7 つ（ドキュメント・型・lint・整形・テストとカバレッジ・ビルド・画面を通したテスト）と決めた
- #33 の脅威のモデル（T-18）で、CI に `pnpm audit --prod --audit-level high` の段を足した。けれども、それを決めた ADR もルールも無く、確認の数は 7 のままだった（`.github/workflows/ci.yml`、2026-11-20）
- #37 は、これを 8 つ目の確認として決めることを求める
- 監査の結果は、変更の中身ではなく、その日の脆弱性のデータベースで決まる。同じ commit が、ある日は通り、次の日は落ちる

## 決定

- **CI は GitHub Actions。`main` への push と全ての PR で動かす。** ADR-0020 の決定（落ちたら全体が失敗、CI が通っていない変更は完了としない、push の前に `pnpm verify`、`main` が赤なら最優先で直す、確認を弱めない、版は `.nvmrc` と `packageManager` から読む）は、全部そのまま引き継ぐ
- **確認は 8 つ。** 8 つ目の `pnpm audit --prod --audit-level high`（本番の依存の高と重大の脆弱性）を、ビルドが要らないので最初に動かす。続けて ADR-0020 の 7 つを同じ順で動かす

| 順 | 確認 | コマンド |
|---|---|---|
| 8（最初） | 本番の依存の監査 | `pnpm audit --prod --audit-level high` |
| 1 | ドキュメント | `pnpm docs:check` |
| 2 | 型 | `pnpm typecheck` |
| 3 | lint | `pnpm lint` |
| 4 | 整形 | `pnpm format:check` |
| 5 | テストとカバレッジ | `pnpm test --coverage` |
| 6 | ビルド | `pnpm build` |
| 7 | 画面を通したテスト | `pnpm test:e2e` |

- **手元の `pnpm verify` は 1〜7 のまま。** 監査は CI だけで動かす。完了の定義の「`pnpm verify` が 0 で終わった（7 つの確認）」は変えない
- 監査が赤になったら、依存を上げて直す。`--ignore` や `--audit-level` を下げて通さない
- CI のジョブの名前は `verify (8 gates)`。まっさらな clone の確かめ（ADR-0069）は別のジョブ

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **8 つ目として最初に、CI だけで（採用）** | 数秒で止まる。完了の定義と全部の PBI の文言を変えずに済む | 手元で通っても CI で落ちることがある（脆弱性が公開された日） |
| 8 つ目として最後に | 番号と順が一致する | 脆弱性があっても、10 分のテストのあとでしか分からない |
| `pnpm verify` にも入れる | 手元と CI が同じ | 監査はネットワークとその日のデータで決まり、変更と関係なく手元の確認が落ちる。完了の定義と全部の PBI の「7 つの確認」を書き換えることになる |
| 監査を CI に入れない（Dependabot だけ） | CI が速い | 脆弱な依存のまま `main` に入る |

## 結果

- 良くなること: 本番の依存に高か重大の脆弱性がある変更は、CI が数秒で止める。確認の数とその理由が 1 か所に書いてある
- 受け入れる負担: 変更と関係なく、新しく公開された脆弱性で CI が赤になる日がある。そのときは依存を上げる変更を先に入れる
- 守ること: 確認を減らす・弱めるのは、新しい ADR でも行わない（ADR-0020 から変わらない）
