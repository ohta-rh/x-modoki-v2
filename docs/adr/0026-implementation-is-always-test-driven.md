# ADR-0026: 実装は必ずテスト駆動（TDD）で行い、失敗したテストの記録を残す

- ステータス: 採用
- 日付: 2026-11-18
- 決定者: ユーザー（実装は必ず TDD）／エージェント（中身と記録の形）
- 関連: ADR-0013、ADR-0021、ADR-0023、ADR-0024、ADR-0025

## 背景

ユーザーは 2026-11-18 に「実装は必ず TDD でやるルールにする」と指示した。

これまでのルールは「テストを先に書いて実装する」と 1 行で書いていただけで（`.claude/rules/delivery-loop.md`）、何をもって先に書いたとするか、守ったことをどう示すかを決めていなかった。

カバレッジ 100%（ADR-0021）は、あとからテストを足しても満たせる。あとから書いたテストは、書いた実装をなぞるので、実装が間違っていても通る。テストが先に落ちるのを見ていなければ、そのテストが何かを確かめているかどうかも分からない。エージェントは、実装を先に書いて、通るテストをあとから足すほうへ流れやすい。

## 決定

- **動くコードは全て、赤 → 緑 → 整理 の順で書く。** 1 つの振る舞いごとに繰り返す
  1. **赤**: その振る舞いを確かめるテストを 1 つ書く。動かして、**期待した理由で落ちる**ことを確かめる
  2. **緑**: そのテストを通す最小の実装を書く。全部のテストが通ることを確かめる
  3. **整理**: テストを通したまま、重複と名前を直す
- **落ちるテストが無いうちは、本番のコードを書かない。** 先に書いてしまったコードは消して、テストから書き直す
- 「期待した理由」とは、確かめたい振る舞いが無いこと。構文のエラー・読み込みの失敗・テストの書き間違いで落ちたものは、赤として数えない
- **不具合の修正は、その不具合を再現して落ちるテストから始める**
- 画面の振る舞いは外側から書く。受け入れ条件の Playwright のテストを先に書いて落とし、その中で、単体とデータアクセス層のテストを赤 → 緑で進める
- **対象**: `src/`・`app/api/**/route.ts`・`proxy.ts`・`scripts/`・`e2e/` の補助の関数
- **対象の外**: 設定のファイル、`drizzle-kit` が作る SQL、shadcn/ui から取り込んだ `src/shared/ui/kit/`、表の宣言（`src/shared/db/schema/`）、型だけのファイル、捨てる場所での調査のコード。`app/**/page.tsx`・`layout.tsx`・`default.tsx` は単体のテストを書けないので、先に Playwright のテストを書いて落とす
- **赤の記録を、試験レポートの「TDD の記録」に残す**（ADR-0025）。振る舞いごとに、テストの名前と、落ちたときの出力の要点を書く。記録の無い TDD は、TDD として数えない
- 完了の定義に 1 項目足す。項目は 9 つになる
- 細目は `.claude/rules/tdd.md` に置く

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 必ず TDD。赤の記録を試験レポートに残す（採用） | テストが実装より先にあったことを示せる。落ちるのを見たテストだけが残る。設計がテストしやすい形になる | 書く順が縛られる。記録の手間がかかる |
| テストを同じ commit に入れるだけ（これまで） | 手間が無い | あとから足したテストと区別できない |
| 赤の commit と緑の commit を分ける | Git の履歴で証明できる | 落ちる commit が `main` に入り、CI が落ちる（ADR-0020 に反する） |
| カバレッジ 100% だけで足りるとする | 追加のルールが無い | 行が動いたことしか示さない。実装をなぞったテストでも満たせる |
| ミューテーションのテストで、テストの質を測る | テストが実際に間違いを見つけるかを機械で測れる | 遅い。道具を足すことになる。必要になったら別の ADR で決める |

## 結果

- 残るテストは全部、落ちるのを一度は見たもの
- 1 つの振る舞いずつ進むので、変更が小さくなり、落ちたときに原因が近い
- 設定や生成されたコードには当てはめない。線引きは「対象の外」の一覧だけで、足すときは ADR を書く
- ここまでに書いた `scripts/check-docs.mjs` と `scripts/chrome-evidence.mjs` は、テストを先に書いていない。骨組みの PBI（#15）で、今の振る舞いを固定するテストを足す。それより後の変更は TDD で行う
