# ADR-0050: 使わなくなった接続は 100ms で閉じる

- ステータス: 採用
- 日付: 2026-11-19
- 決定者: エージェント（委任された判断。ADR-0028 によりユーザーに聞かずに決めた）
- 関連: [ADR-0037](0037-pool-closes-when-idle-not-after-response.md)（その「1 秒」をこの ADR で置き換え）、ADR-0017、#59、#55

## 背景

- ADR-0037 は、リクエストごとの pool を `end()` せず、`idleTimeoutMillis: 1_000` で使わなくなった接続を閉じると決めた
- 接続は要求が終わったあとも 1 秒残るので、開いている接続の数はおよそ「1 秒あたりの要求の数 × 要求ごとの接続の数」になる
- 2026-11-19 の計測（#59）: `GET /api/timeline/following?cursor=` を 600 回、60 本ずつ並べて送ると、1 秒のままでは 493 回が `sorry, too many clients already` で 500（idle の接続 279、`max_connections` は 300）。100ms では 600 回とも 200（idle は最大 114）

## 決定

- **`getDb()` の pool の `idleTimeoutMillis` を 100 にする。** ほかの決定（`end()` しない、`max: 2`、要求ごとの pool、モジュールの一番上で作らない）は ADR-0037 と ADR-0017 のまま
- 1 つの要求の中で続けて走る問い合わせは、100ms のあいだ同じ接続を使い回せる

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **100ms（採用）** | 変えるのは 1 つの数だけ。たまる接続が 10 分の 1 | 問い合わせの間が 100ms より空くと、接続を作り直す（数 ms） |
| 要求の終わりに `end()` する | 接続がすぐに閉じる | ADR-0037 のとおり、`after()` の処理が終わった pool を使ってしまう |
| モジュールに 1 つの pool を共有する | 接続の数が一定 | Cloudflare Workers ではモジュールの接続を要求をまたいで持てない（ADR-0017） |
| `max_connections` を上げる | コードを変えない | たまる速さは同じで、上限を先へ送るだけ |

## 結果

- 良くなること: 要求が多いときも接続が上限に届きにくい
- 受け入れる負担: 1 つの要求の中で間が空くと接続を作り直す
- 守ること: 接続を長く持つ設定に戻さない。Route Handler では React の `cache()` が効かず `getDb()` のたびに pool ができる点は、別に扱う
