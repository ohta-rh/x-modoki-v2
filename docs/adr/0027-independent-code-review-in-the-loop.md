# ADR-0027: PBI ごとに、push の前に、独立した sub agent（opus）のコードレビューを受ける

- ステータス: 採用（3 回で `blocked` にする決まりを ADR-0028 で置き換え）
- 日付: 2026-11-18
- 決定者: ユーザー（ループに、独立した sub agent の opus によるコードレビューを入れる）／エージェント（手順と形）
- 関連: ADR-0020、ADR-0023、ADR-0024、ADR-0025、ADR-0026

## 背景

ユーザーは 2026-11-18 に「ループにコードレビュー（独立した sub agent の opus）を入れる」と指示した。

このリポジトリは `main` に直接 push して進め、PR を作らない（ADR-0020）。人が差分を読む場所が無い。ここまでの確認（TDD・カバレッジ 100%・CI・Chrome での確認）は、どれも書いた側が自分で行う。書いた側は、自分が思いつかなかった入力や、自分で決めた前提の間違いを、自分のテストでは見つけられない。同じ日に、機械の確認が全部通っていた issue の本文の崩れと、撮った写真の切れを、見て初めて見つけている。

書いた側と同じ文脈を持つエージェントに「もう一度確かめて」と頼んでも、同じ前提をなぞるだけで、独立した確認にならない。

## 決定

- **コードを変える PBI は全て、push の前に、独立した sub agent のコードレビューを受ける。** ループの手順の 1 つとし、完了の定義に 1 項目足す（項目は 10 になる）
- **レビューする sub agent は `.claude/agents/code-reviewer.md`。** モデルは定義の中で `opus` に固定する。呼ぶ側が指定し忘れても、書いた側のモデルで動かない
- **独立させる。** レビューする側に渡すのは、issue の番号と、差分の範囲だけ。書いた側の考え・要約・「ここは大丈夫」を渡さない。レビューする側は、issue・ルール・ADR・差分を自分で読む
- **読むだけにする。** 使える道具は Read・Grep・Glob・Bash で、ファイルを変えない・commit しない。直すのは書いた側
- レビューが見るのは、正しさ・受け入れ条件・安全性・テストと TDD・構造（FSD）・Workers の制約・範囲と決定。整形とリンターが見るもの、好み、確かめていない推測は指摘させない
- **指摘が 0 件は、正しい結果の 1 つ。** レビューする側には、確かめられない指摘を捨てるよう求める
- **書いた側は、指摘を 1 つずつ自分で確かめてから動く。** 正しければ、落ちるテストを先に書いて直す（ADR-0026）。間違いなら、根拠を付けて退ける。うのみにして直さない・確かめずに退けない
- 判定が `CHANGES_REQUESTED` なら、直したあと、**新しい** sub agent でもう一度レビューする（前の回の文脈を引き継がせない）。3 回で承認にならなければ、issue に経過を書いて `blocked` にする
- **結果を、試験レポートの「コードレビュー」の節に残す**（ADR-0025）。判定・回数・指摘ごとの対応（直した commit とテスト、または退けた理由）を書く
- コードを変えない PBI（文書だけ）は、レビューを受けず、試験レポートに「コードの変更なし」と書く
- 順番は、`pnpm verify` と Chrome での確認のあと、push の前。直したら `pnpm verify` からやり直す

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 文脈を持たない、読むだけの opus の sub agent。push の前（採用） | 書いた側の前提に引きずられない。`main` に入る前に止まる。判断の要る作業に合うモデル | PBI ごとに時間と費用がかかる。間違った指摘も出る |
| 書いた側が、自分でもう一度読む | 費用が無い | 同じ前提をなぞる。独立していない |
| PR を作って、GitHub の上でレビューする | レビューの記録が GitHub に残る | `main` に直接 push する進め方を変えることになる。人が見ない PR は、待ちを増やすだけ |
| push したあとにレビューする | 手順が止まらない | 間違いが `main` に入ってから見つかる |
| 複数の sub agent で観点ごとにレビューする | 見落としが減る | PBI ごとには重い。指摘が増え、確かめる手間が増える。1 つで足りなければ、別の ADR で決める |
| sonnet か haiku のレビュー | 安い | レビューは判断の作業で、ここを安くすると意味が薄れる |
| レビューする側に直させる | 往復が減る | 直した側を誰もレビューしない。独立が崩れる |

## 結果

- `main` に入る全部のコードの変更を、書いた側ではない目が一度読んでいる
- PBI ごとに、レビューと、指摘の確かめ直しの時間がかかる
- レビューする側の間違った指摘に時間を使うことがある。「確かめてから報告する」「確かめてから動く」の 2 段で減らす
- レビューの定義（何を見るか）は `.claude/agents/code-reviewer.md` の 1 か所。ルールや ADR を足したら、そこも直す
- 完了の定義が 10 項目になる。ルールと、開いている全部の PBI の本文を、同じ変更で直す
