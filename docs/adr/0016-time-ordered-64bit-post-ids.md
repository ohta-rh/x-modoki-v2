# ADR-0016: 投稿の ID は、時刻の順に並ぶ 64 bit の整数をアプリで作り、外では文字列として扱う

- ステータス: 採用
- 日付: 2026-11-18
- 決定者: エージェント（委任された判断）
- 関連: [データモデル](../architecture/data-model.md)、ADR-0009、ADR-0015

## 背景

投稿の ID は URL（`/{username}/status/{id}`）に出る。X の投稿の ID は、時刻の順に並ぶ 64 bit の数字。URL の形を X に合わせる（ADR-0009）。

タイムラインは、投稿の ID をカーソルにしてページングする（ADR-0015）。ID が作った時刻の順に並んでいれば、ID だけで新しい順に並べられ、時刻と ID の 2 つを比べる必要が無い。連番にすると、投稿の総数と増える速さが外から分かる。

## 決定

- **投稿の ID は 64 bit の整数。** 上の 41 bit が基準の時刻（2026-01-01T00:00:00Z）からのミリ秒、下の 22 bit が乱数。符号の bit は使わない
- アプリ（`src/lib/id.ts`）で作る。データベースの連番と `uuidv7()` は使わない
- データベースの型は `bigint`。Drizzle では `bigint({ mode: 'bigint' })` で読む
- **データアクセス層の出口で、必ず文字列にする。** DTO・JSON・URL・Zod のスキーマでは文字列（数字だけの 1〜19 桁）として扱う
- 主キーの違反になったら、ID を作り直して 1 回だけやり直す
- ユーザーの ID は Better Auth が作る文字列のまま使う（ADR-0007）。通知など、ほかの表の ID も同じ作り方にする

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 時刻と乱数の 64 bit の整数（採用） | URL が X と同じ形。ID だけで新しい順に並ぶ。総数が分からない | JavaScript の `number` に入らないので、文字列への変換が要る |
| UUIDv7 | データベースで作れる。時刻の順に並ぶ | URL が長く、X の形にならない |
| データベースの連番 | 最も単純 | 総数と増える速さが外から分かる |
| 時刻と機械の番号と連番（元の Snowflake） | ぶつからない | インスタンスは 1 つで、機械の番号を配る仕組みは要らない |
| ULID・NanoID | 文字列でそのまま使える | 数字だけの URL にならない |

## 結果

- カーソルは ID の 1 つで済み、索引も ID だけで足りる
- 同じミリ秒に 2 つ作ったとき、乱数がぶつかる確率は約 400 万分の 1。ぶつかっても主キーが守り、やり直しで解決する
- `bigint` をそのまま `JSON.stringify` に渡すと例外になる。出口での変換を忘れるとすぐ分かる
- 41 bit のミリ秒は、基準の時刻から約 69 年ぶん使える
